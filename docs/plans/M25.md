## 2. 架構決策

### 2.1 兩個入口共用同一張快照表

```
入口 A：L0 首頁 <TradeQualityAnalysis />（既有，使用者手動輸入）
入口 B：L0 自選清單表格（新增，依 watchlist 自動跑）
入口 C：cron（新增，每日跑全使用者全 watchlist）
                            ↓ 寫入 ↓
        watchlist_trade_quality_snapshots
        (user_id, stock_id, buy_date, snapshot_trade_date) UNIQUE
```

- 三個入口都寫同一張表，`source` 欄位區分：`manual` / `on_demand` / `cron`
- 表格層查詢一律 `WHERE user_id = current_user`，**不跨使用者污染**
- 同 `(user_id, stock_id, buy_date, snapshot_trade_date)` 已存在 → 直接沿用，不重打 OpenAI
- 累積出來的歷史快照 = delta layer 比對的資料來源

### 2.2 snapshot_trade_date 規則（同 signal archive）

**核心問題：什麼時候算「今天的快照」、什麼時候要重跑？**

借用 `run_signal_archive_returns.py` 既有規則：

```python
TAIPEI_TZ = ZoneInfo("Asia/Taipei")
ETL_DONE_TIME = time(hour=20, minute=0)  # 假設 ETL 18:00 開跑、20:00 前完成

def resolve_snapshot_trade_date(db, *, now=None) -> Optional[date]:
    """
    回傳「該用哪一個交易日當 snapshot_trade_date」。
    - 開盤日 20:00 ~ 隔天 19:59 → 該交易日
    - 假日 / 休市 → 自動回退到最近一個 daily_price 有資料的交易日
    """
    now_tpe = now or datetime.now(TAIPEI_TZ)
    ceiling = (
        now_tpe.date() if now_tpe.time() >= ETL_DONE_TIME
        else now_tpe.date() - timedelta(days=1)
    )
    return (
        db.query(func.max(DailyPrice.trade_date))
        .filter(DailyPrice.trade_date <= ceiling)
        .scalar()
    )
```

- ETL 18:00 開跑、預估 18:30~19:30 完成；保守 `ETL_DONE_TIME = 20:00`（給 retry buffer）
- 20:00 前打 trade quality → 用前一個交易日的快照（避免吃到未完整的當日 ETL）
- cron 跑時間 = 台北 20:30（ETL 完成後）

### 2.3 失敗處理

cron 對某檔 OpenAI 失敗：
- 寫一筆 `error_message` 進快照表（仍佔用 unique key）
- 表格查詢時：如果今天的快照是 `error` 狀態 → **fallback 顯示上一次成功快照** + 灰色標「資料較舊（YYYY-MM-DD）」+ 重試按鈕
- 若沒有任何成功快照 → 顯示「分析失敗、點重試」

## 3. DB schema

### 3.1 新表 `watchlist_trade_quality_snapshots`

```python
class WatchlistTradeQualitySnapshot(Base):
    __tablename__ = "watchlist_trade_quality_snapshots"

    id = Column(Integer, primary_key=True, autoincrement=True)
    user_id = Column(Integer, ForeignKey("users.id", ondelete="CASCADE"), nullable=False, index=True)
    stock_id = Column(String(20), nullable=False, index=True)
    buy_date = Column(Date, nullable=False)        # 使用者填的買進日（同 user_watchlist.buy_date）
    snapshot_trade_date = Column(Date, nullable=False, index=True)  # 跑分析時用的交易日

    # M17 trade quality 完整 payload（與 TradeQualityResponse 對齊）
    rating = Column(String(20), nullable=True)              # STRONG_BUY/BUY/NEUTRAL/WATCH/RUN
    rating_label = Column(String(40), nullable=True)
    classification = Column(String(2), nullable=True)       # A/B/C
    market_state = Column(String(20), nullable=True)
    quadrant = Column(String(8), nullable=True)
    expectation_gap = Column(String(20), nullable=True)
    action = Column(String(40), nullable=True)
    summary = Column(Text, nullable=True)
    core_logic = Column(Text, nullable=True)
    risk_level = Column(String(20), nullable=True)
    target_price_low = Column(Float, nullable=True)
    target_price_high = Column(Float, nullable=True)
    time_horizon_days = Column(Integer, nullable=True)
    exit_price_low = Column(Float, nullable=True)
    exit_price_high = Column(Float, nullable=True)
    max_holding_days = Column(Integer, nullable=True)
    report_markdown = Column(Text, nullable=True)
    key_factors = Column(JSON, nullable=True)               # 新增：[{category, level, trend, note}]

    # Cache / 觸發 metadata
    source = Column(String(16), nullable=False)             # manual / on_demand / cron
    status = Column(String(16), nullable=False, default="ok")  # ok / failed
    error_message = Column(Text, nullable=True)             # status=failed 時填
    generated_at = Column(DateTime, default=datetime.utcnow, nullable=False)

    __table_args__ = (
        UniqueConstraint(
            "user_id", "stock_id", "buy_date", "snapshot_trade_date",
            name="uq_wtqs_user_stock_buy_snapshot",
        ),
    )
```

## 4. Prompt 修改：加 `key_factors` 結構化欄位

### 4.1 修改點

`backend/app/prompts/trade_quality.md` PART 1 JSON schema 內加：

```json
{
  // 既有欄位全保留 ...
  "key_factors": [
    { "category": "industry",       "level": "A|B|C", "trend": "improving|stable|weakening|deteriorating", "note": "10~25 字中文" },
    { "category": "industry_heat",  "level": "...",   "trend": "...",      "note": "..." },
    { "category": "return",         "level": "...",   "trend": "...",      "note": "..." },
    { "category": "chip",           "level": "...",   "trend": "...",      "note": "..." },
    { "category": "technical",      "level": "...",   "trend": "...",      "note": "..." },
    { "category": "fundamental",    "level": "...",   "trend": "...",      "note": "..." }
  ]
}
```

### 4.2 規則

- `category` enum 固定 6 個：`industry / industry_heat / return / chip / technical / fundamental`
- `level` enum：`A`（強，綠燈）/ `B`（中，黃燈）/ `C`（弱，紅燈）
- `trend` enum：`improving / stable / weakening / deteriorating`（給 delta layer 用箭頭）
- `note` 中文一句話，10~25 字

### 4.3 規則對齊 M21

- `industry_heat` 直接吃 `industry_summary.industry_hot_level`（S → A、A → A、B → B、C → C）
- `chip` 直接吃 `chip_summary.chip_strength`
- `technical` 對應 `price_structure.trend` + `is_breakout`
- `fundamental` 對應 `fundamental.revenue_yoy`

可寫進 prompt：「請以 M21 訊號為主、不要重新從 raw 推算」。

### 4.4 兼容性

- TradeQualityResponse 加 `key_factors: Optional[List[KeyFactor]] = None` —— **舊客戶端忽略此欄位仍可運作**
- `_normalize_response` 對 `key_factors` 做 enum validation，不合法的 row 直接 drop（不 raise）

## 5. Backend 改動

### 5.1 既有 `analyze_trade_quality` 接 cache（同檔案 `routers/analysis.py`）

流程改寫：

```
POST /api/analysis/trade-quality (existing)
  ↓
resolve_buy_date(db, req.buy_date)
  ↓
resolve_snapshot_trade_date(db)        ← 新 helper
  ↓
讀 cache：WHERE user_id + stock_id + buy_date + snapshot_trade_date
  ↓ hit (status=ok) ?
       ├ yes → 直接回傳（不打 OpenAI）
       └ no  → 跑 _collect_context / _call_openai / _normalize_response
                ↓
                寫快照表（source='manual', status='ok'）
                ↓
                回傳
```

注意：
- 未登入使用者（`user is None`）→ 仍走原本 5 分鐘 in-memory cache，**不寫 DB**（無 user_id 可關聯）
- 登入使用者每次跑都寫快照表，自動累積 delta 用的歷史
- 既有 `_get_cached_trade_quality / _store_cached_trade_quality` in-memory cache 保留作為 hot path（DB query 前先看一次）

### 5.2 新 endpoint `GET /api/watchlist/trade-quality`

讀全清單最新快照：

```python
@router.get("/watchlist/trade-quality")
def list_watchlist_trade_quality(
    user: User = Depends(require_user),
    db: Session = Depends(get_db),

    """
    回傳當前使用者 watchlist 每檔的最新 trade quality 快照 + 上一次快照（給 delta 用）。
    沒快照的個股 row 仍回傳但 latest=null（前端顯示「分析中」並觸發 refresh）。
    """
```

Response schema：
```typescript
{
  items: [
    {
      stock_id: string,
      stock_name: string,
      buy_date: date,
      latest_close: number | null,
      change_pct: number | null,           // 相對昨日漲跌幅
      latest: {

        key_factors: KeyFactor[],
```

### 5.4 cron script `backend/run_watchlist_trade_quality.py`

```python
"""
Daily watchlist trade quality refresh (M25).

執行流程：
1. resolve_snapshot_trade_date(db)
2. SELECT DISTINCT user_id, stock_id, buy_date FROM user_watchlist
3. 對每組 (user_id, stock_id, buy_date)：
   - 若 (user_id, stock_id, buy_date, snapshot_trade_date) 已有 ok 快照 → skip
   - 否則跑 trade quality → 寫快照表（source='cron'）
4. exit code: 0 ok / 1 partial（有失敗但部分成功）/ 2 全失敗 / 5 holiday
"""
```

時程預估：
- 每使用者 ~10 檔 × N 使用者 ≈ 10~100 檔/天
- 每檔 ~5~25s（OpenAI），全部 sequential ~5~40 min
- 失敗的 row 寫 status='failed'，不中斷整個 job

### 5.5 GitHub Actions 整合

修改 `.github/workflows/daily_etl_update.yml`，在 `Evaluate final status` 之後新增 step：

```yaml
- name: Run watchlist trade quality refresh
  if: steps.etl1.outputs.etl_exit == '0' || steps.etl1.outputs.etl_exit == '1' || steps.etl2.outputs.etl_exit == '0' || steps.etl2.outputs.etl_exit == '1'
  working-directory: backend
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
    OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
    OPENAI_MODEL: ${{ secrets.OPENAI_MODEL }}
  run: |
    set +e
    python3 run_watchlist_trade_quality.py --date ${{ steps.resolve.outputs.target_date }}
    WTQ_EXIT=$?
    echo "watchlist_trade_quality exit code: $WTQ_EXIT"
    # 不讓 wtq 失敗影響 ETL workflow 結果（wtq 是 enrichment、ETL 才是 critical）
    exit 0
```

關鍵：
- 條件 `etl exit == 0 or 1`（partial）才跑 wtq；ETL 完全失敗 → 跳過 wtq
- ETL `holiday`（exit 5）→ 跳過 wtq（沒新交易日資料）
- timeout 從 240 min 提高到 300 min（多給 60 min 給 wtq）

## 8. 已知 Gotcha 與風險

1. **OpenAI 成本**：每使用者 30 檔 × $0.05/檔 = $1.5 USD/天/使用者；10 使用者 = $15/天 = $450/月。先觀察、必要時降為每 3 天跑一次或拔 cron 改純 on-demand。
2. **18:00 ETL 與 FinMind 同步邊界**：已確認維持 18:00 不動；`snapshot_trade_date` 規則 `ETL_DONE_TIME=20:00` 確保使用者打點時不會吃到不完整的 ETL 結果。
3. **未登入使用者寫不寫快照**：**不寫**（沒 user_id 可關聯，避免 NULL user_id row 污染）；走原本 5 分鐘 in-memory cache。
4. **prompt schema 演進**：`key_factors` 是新增 optional 欄位；舊 LLM 輸出（沒這欄）→ `_normalize_response` 回傳 `key_factors=None`，前端隱藏條列區塊但其他功能不受影響。
5. **delta layer 的 enum 跨版本相容**：若未來 prompt 改了 category enum（例如把 `industry_heat` 拆成 `heat_score / heat_capital_type`）→ 舊快照的 category 在新版本前端可能無法 render；用 unknown category 直接顯示 `note` 文字、不顯示燈號顏色。
6. **cron 失敗 + watchlist 大幅變動**：使用者今天加 5 檔到 watchlist、cron 跑時這 5 檔還沒寫進 user_watchlist → 隔天才會被 cron 抓到；中間使用者打開首頁 → on-demand refresh fallback 補洞。
7. **ETL retry sleep 5400s 期間**：ETL exit 2 → sleep 1.5h → retry → 接著跑 wtq；wtq 可能延後到台北 21:00~22:00 才開跑；不影響使用者隔天看（早上 7:00 早就跑完）。
